# Pickups — lifecycle

- lifecycle (task-027-01, DRGS-like, [[xp-level-up]]): spawned at a cell center (grid) or at robot feet (XP). Pop: random yaw (or `SetPopYaw` before BeginPlay), distance random in [`PopMinDistance`, `PopMaxDistance`]; horizontal ease-out over `PopDuration`; vertical main arc of `PopArcHeight` from spawn Z to spawn Z + `HoverHeight` over the first 1 - `PopBounceFraction` of the pop, then a bounce of `PopBounceHeight` (`PopFallTimeRatio` can slow the descent of the main arc, see floaty pop below). Rest: `AttractDelay` from the end of the pop, never attracted meanwhile (unless `bAttractDuringPop`, see mid-air magnet below). Magnet: first frame after the rest with the 2D distance to the miner within its `PickupRadius`: latches (keeps flying even if the miner leaves the radius), `OnMagnetStart`, speed starts at `MagnetStartSpeed` and gains `MagnetAcceleration` per second up to `MagnetMaxSpeed` (applied before each step), straight 3D line to the miner; nearby cubes latch together and form a stream. Heal refusal (task-089-01, [[heal-ore]]): `IsRefusedByMiner` is true for a Heal pickup when the miner Health >= MaxHealth; in Rest it is checked after the radius test, so a refused pickup stays at its rest point and latches on the first frame the miner is damaged and in radius (re-checked each frame, no event binding, nothing for XP and ore); in Magnet it is checked at the start of each `FlyToMiner` step: a pickup in flight when the miner reaches full health (another heal collected first, same frame included) goes back to Rest where it is, snapped to its rest Z, `MagnetSpeed` 0, never consumed; no despawn. A partial heal is collected and clamped at MaxHealth by the effect (95 / 100 + 15 = 100). No `OnMagnetStop` event (`BP_PickupHeal` has no trail nor `OnMagnetStart` handler, so nothing stays on). Collect within `CollectDistance` (or when the step reaches it): Verbose log; an XP pickup calls `AddXP(XPAmount)` ([[sys-progression]]); a Heal pickup calls `ApplyHeal`: `HealEffectClass` (`URRGE_Heal` by default) with SetByCaller `Data.Heal` = `HealAmount` applied to the miner ASC, skipped when the amount is 0, the miner is dead or has no ASC ([[sys-gas-core]]); `ARRMiner::NotifyPickupCollected(Type, Location)` broadcasts `OnPickupCollected(Type)` then `OnPickupCollectedAt(Type, Location)`; Blueprint event `OnCollected(Location)`; released to the actor pool when a pool member, else destroyed (task-092-01).
- properties (all `EditDefaultsOnly`, provisional, task-027-01 values): `PickupType` Ore, `OreValue` 1 (task-070-01; set per chunk by the grid from the deposit's `ChunkValue`, [[ore-economy]]; nothing consumes it yet), `XPAmount` 1 (set per cube by the robot), `HealAmount` 0 (C++ default, read only by Heal pickups; `BP_PickupHeal` does not override it; task-088-02: the grid sets it per pickup from the deposit `HealValue`, `OreTypes.csv` row `Heal` = 15, so a 2 × 2 vein restores 60; a heal pickup spawned outside the grid heals nothing), `HealEffectClass` `URRGE_Heal`, `PopMinDistance` 80 uu, `PopMaxDistance` 220 uu, `PopDuration` 0.35 s, `PopArcHeight` 80 uu, `PopBounceHeight` 15 uu, `PopBounceFraction` 0.25, `PopFallTimeRatio` 1 (task-195-01), `HoverHeight` 30 uu, `AttractDelay` 1.0 s, `bAttractDuringPop` false, `PopAttractDelay` 1.2 s (task-195-01), `MagnetStartSpeed` 400 uu/s, `MagnetAcceleration` 4000 uu/s2, `MagnetMaxSpeed` 2500 uu/s, `CollectDistance` 50 uu. Measured at 60 fps: arc peak 95 uu, bounce peak 45 uu, rest at 0.350 s; first magnet frame 466.7 uu/s, cap 2500.
- floaty pop (task-195-01, owner 2026-10-15, provisional; reference DRGS XP orbs): `PopFallTimeRatio` (float, `EditDefaultsOnly`, `BlueprintReadOnly`, category `Pickup|Pop`, default 1, ClampMin 0.1) = fall time / rise time of the main arc. Arc computation in `UpdatePop`: Alpha = PopElapsed / PopDuration; the main arc spans Alpha in [0, ArcEnd = 1 - PopBounceFraction], T = Alpha / ArcEnd; the arc is the symmetric curve Z = Lerp(PopStart.Z, PopEnd.Z, S) + PopArcHeight x 4 S (1 - S) of a parameter S, and the ratio remaps T to S piecewise linearly so that the apex S = 0.5 is reached at Ta = 1 / (1 + ratio): S = 0.5 T / Ta before it, 0.5 + 0.5 (T - Ta) / (1 - Ta) after (ratio 1: the code skips the remap, S = T, exactly the former arc). Each half stays a parabola, so the fall gravity is 1 / ratio² of the rise one (ratio 2: rise one third of the arc, fall two thirds, fall gravity a quarter). Horizontal easing choice: the ease-out 1 - (1 - a)² runs on the remapped time (a = S x ArcEnd during the arc, Alpha during the bounce), so the path in space is exactly the symmetric one and only the speed along it changes (fast rise, slow drifting descent); continuous at the arc end. The bounce and the total `PopDuration` are unchanged. With the task-195-02 values (PopDuration 1.6 s, PopBounceFraction 0.25 kept, ratio 2): arc 1.2 s, apex at 0.4 s about PopArcHeight + HoverHeight / 2 above the spawn (250 + 15 uu), fall 0.8 s, then the 0.4 s bounce. A small kink in vertical speed at the apex comes from the Lerp term (HoverHeight-sized, halved after the apex): negligible, not measured.
- mid-air magnet (task-195-01, owner 2026-10-15, provisional): `bAttractDuringPop` (bool, default false = former behaviour) and `PopAttractDelay` (float s, default 1.2, `EditCondition = bAttractDuringPop`), both `EditDefaultsOnly`, `BlueprintReadOnly`, category `Pickup|Collect`. With the option, in Pop, at the top of each `UpdateMotion` (the existing `URRPickupSubsystem` loop, or the fallback tick; no new tick, no timer), once `PopElapsed` (time since the life started: fresh spawn or pool reuse) >= `PopAttractDelay`, `TryLatchMagnet` runs the same latch as from Rest: 2D distance within `PickupRadius`, `IsRefusedByMiner` (a refused heal does not latch, keeps popping, then rests), latch on the miner, Magnet phase, glow target 0, `MagnetStartSpeed`, `OnMagnetStart`, first `FlyToMiner` step the same frame instead of the pop step. A latched pickup drops the rest of its pop: it flies the straight 3D line from its mid-air point to the miner, like the magnet from Rest (`PopEnd` is kept, used only by `ReturnToRest`). On the ground, with the option, the wait ends at `AttractDelay` after landing or `PopAttractDelay` after spawn (`GetLifeElapsed` = `PopElapsed` + `RestElapsed`), whichever comes first: with the task-195-02 values (pop 1.6 s, delay 1.2 s) a pickup is attractable from 1.2 s, in the air or as soon as it lands. A heal latched mid-air then refused in flight (`ReturnToRest`) is snapped to its rest Z where it is (up to the arc height lower; rare, not seen) and may latch again at once. Reset per life: no new state; `PopElapsed` and `RestElapsed` are already reset by `StartLife` and `OnPoolReleased`. Unverified: no test covers the ratio nor the mid-air latch (none added, per the task); no visual check.
- glow fade (task-148-01, provisional, owner 2026-10-13): `bGlowFade` (default false), `GlowFadeDuration` 0.2 s, `GlowFadeDataIndex` 0 (all `EditDefaultsOnly`, category `Pickup|Glow`). For a pickup with `bGlowFade`, a fade value 0..1 (`GlowFade`) moves toward a target (`GlowFadeTarget`) at 1 / `GlowFadeDuration` per second (0 s = instant) and is written with `UPrimitiveComponent::SetCustomPrimitiveDataFloat(GlowFadeDataIndex, value)` on `PickupMesh` each time it changes (no dynamic material instance). Target: 0 during Pop, 1 at the start of Rest (landing, also `ReturnToRest`), 0 at the start of Magnet and at Collected (the pickup is released the same frame, so the Magnet fade-out is what shows). Updated at the top of `ARRPickup::UpdateMotion`, i.e. in the existing `URRPickupSubsystem` loop (or the fallback tick), only while the value differs from the target (one frame after the phase change; no new tick, no timer). Reset: `ResetGlowFade` in `StartLife` (fresh spawn and pool reuse) and `OnPoolReleased` sets value and target to 0 and writes 0, so a fresh or pooled pickup never shows the material default nor flashes. `bGlowFade` false (ore, heal, C++ default): no write, no behaviour change. The material side (scalar parameter with Use Custom Primitive Data at index 0) and `bGlowFade` true on `BP_PickupXP` / `BP_PickupXPBig` come with task-148-02.
- look per life (task-192-01, owner 2026-10-15, defaults accepted; per-Blueprint values provisional, set in task-192-02 and task-189-05): `RestOrientation` (`ERRPickupRestOrientation`, `EditDefaultsOnly`, `BlueprintReadOnly`, category `Pickup|Look`, default `None`) and `MeshVariants` (`TArray<TObjectPtr<UStaticMesh>>`, same flags and category, default empty). `ApplyLifeLook`, called at the top of `StartLife` (fresh spawn in BeginPlay and every pool reuse in `OnPoolAcquired`, before the pop target is picked), draws them once per life: a uniformly random non-null entry of `MeshVariants` is set on `PickupMesh` with `SetStaticMesh` (empty list or only null entries = the Blueprint mesh is kept; same mesh drawn again = no-op); then the actor rotation: None leaves it as spawned (zero for grid and robot drops, the pool restores the acquire rotation, zero, on reuse: today's look), YawOnly sets (0, random yaw in [-180, 180], 0), Full sets a uniform random rotation (Shoemake quaternion, any pitch, roll and yaw). The rotation is kept through the pop and the rest (the pop only calls `SetActorLocation`): no tumble in flight, no tick, no timer. `BP_PickupXP` and `BP_PickupXPBig` still turn to face the miner in `OnMagnetStart`, which replaces the drawn rotation at magnet start. Nothing is reset on `OnPoolReleased`: the next life draws again. Material rule: `SetStaticMesh` does not touch `OverrideMaterials` (engine 5.8 `UStaticMeshComponent::SetStaticMesh` only replaces the mesh), so the Blueprint override materials of `PickupMesh` apply by slot index to every variant: variants must share the slot layout the overrides target (the three ore chunks share crystal_bright and crystal_dark), or the overrides must be left empty so each mesh uses its own slot defaults (BP_PickupOre has its override cleared since task-189-05 and uses the slot defaults of the three chunks, [[bp-pickup-ore]]; its `OnMagnetStart` does not turn it, so the ore keeps the drawn rotation to the miner). Verified: build clean; the existing pickup and pool tests pass unchanged (all Blueprints keep None and an empty list); YawOnly, Full and the variant draw are not exercised by a test nor checked visually.
- physics (task-229-02, owner 2026-10-17 "vraie physique Chaos", "collision uniquement sur mur et sol", "très légère rotation"; values provisional): collision object channel `Pickup` (`ECC_GameTraceChannel2`, default response Block so the grid `BlockAll` components block it) and profile `Pickup` in `Config/DefaultEngine.ini`: `PhysicsOnly` (no query, so no trace, sweep or overlap ever sees a pickup), blocks only `WorldStatic` (the grid floor HISM and the rock, ore, heal, special and barrel collision ISMs are all `BlockAll` = WorldStatic), ignores Visibility, Camera, WorldDynamic, Pawn (miner, robots), PhysicsBody, Vehicle, Destructible, Projectile and Pickup (pickups never touch each other). `RRCollisionChannels::Pickup` / `PickupProfile`. `PickupMesh` is Movable with this profile from the constructor, no overlap events, no hit events; `BeginPlay` (`ConfigurePhysicsBody`, once per actor) sets the profile (`PhysicsCollisionProfile`; `NoCollision` when `bPhysicsOnLanding` is false), damping, the depenetration cap and the physical material, and still sets every other primitive to `NoCollision` and `CanCharacterStepUpOn` No. The body uses the mesh simple collision (task-229-01). Flight: the pop stays kinematic (floaty values untouched) and the body is kinematic, moved by teleport; each step also turns the actor by `PopSpinDegPerSec` (default 90 deg/s) about a random unit axis drawn per life in `StartLife` (`SpinAxis`). Landing: when `CanSimulateOnLanding` (`bPhysicsOnLanding`, console variable `rr.Pickup.Physics` 1, a valid body with physics collision; native test pickups without a mesh have none and keep the old motion) the pop ends at the touch-down of the main arc (time (1 - `PopBounceFraction`) x `PopDuration`, 1.2 s with the floaty values): the actor is put at the arc end point, `SetSimulatePhysics(true)`, linear velocity = the arc velocity there (finite difference over 1/60 s) with its horizontal part scaled by `LandingHorizontalSpeedScale` (1) and its vertical part by `LandingVerticalSpeedScale` (0 = horizontal only, per the task default), angular velocity = spin axis x `PopSpinDegPerSec`; the kinematic bounce is skipped (physics bounces it from the hover height); Rest starts there (`AttractDelay` counted from it, glow target 1). Estimated from the floaty values (not measured): horizontal speed at touch-down about 0.23 x the pop distance per second (about 70 uu/s at 300 uu), vertical about 600 uu/s (dropped at scale 0); the pickup then falls from `HoverHeight` (30 uu) onto the floor. Tunables (`EditDefaultsOnly`, category `Pickup|Physics`): `PhysicsLinearDamping` 0.1, `PhysicsAngularDamping` 0.5, `PhysicsFriction` 0.7, `PhysicsRestitution` 0.2 (combined with the floor default material by the project combine mode, average), `PhysicsSleepLinearThreshold` 5 uu/s, `PhysicsSleepAngularThreshold` 0.2 rad/s, `PhysicsSleepCounterThreshold` 4 (engine material defaults 1, 0.05, 4: sleeps sooner), `PhysicsMaxDepenetrationVelocity` 200 uu/s (a pickup landing inside a rock block is pushed out slowly), `PhysicsFallLimit` 500 uu (fall guard: a simulating pickup more than that below `PopEnd` goes kinematic back at `PopEnd`; 0 = off). The physical material is built from the class default (`MakePhysicalMaterial`, class found by path because the module does not link PhysicsCore) and shared per class by `URRPickupSubsystem::FindOrAddPhysicalMaterial`. Magnet: `TryLatchMagnet` calls `StopPhysics` (velocities zeroed, `SetSimulatePhysics(false)`) before the kinematic fly-in (teleport moves). Heal refused in flight (`ReturnToRest`): physics restarts from zero velocity, the pickup falls where it is (snap to the rest Z only without physics). Pool: `OnPoolReleased` calls `StopPhysics`; the pool parks it (collision off, hidden) and restores the transform with `ResetPhysics` at the next acquire, so a life always starts kinematic. `RestOrientation` is only the start orientation of the spin: physics decides how it lies (a pickup without physics keeps the spun orientation, it is never snapped back). `rr.Pickup.Physics 0` = kinematic bounce and rest point as before (body still present, kinematic). Tests: `RogueRigs.Pickups.HealFullHealthWaits` and `HealPartialClamp` (BP_PickupHeal, now physical) check "settled near its rest point, on the floor" instead of the exact rest point and height; the native-pickup motion tests pass unchanged (no body). Cost: [[perf-lead-pickup-simulated-roll]]. Unverified: no capture yet (task-229-03), no check that cubes never rest on a corner, that rolling reads at 70 uu/s, nor how sleeping pickups behave when the rock under them is destroyed.
- pulse per life (task-257-02, owner 2026-10-20, provisional): `PulseSeed` 1, `PulseRateMin` 0.8, `PulseRateMax` 1.2, `PulsePhaseDataIndex` 1, `PulseRateDataIndex` 2 (all `EditDefaultsOnly`, category `Pickup|Glow`). `ApplyPulseDesync`, in `StartLife` (fresh spawn and every pool reuse), for `PickupType` Ore and Heal only (`UsesPulseDesync`): draws the pulse spawn id of the life from `URRPickupSubsystem::DrawPulseSpawnId` (0, 1, 2... per world, in the order Ore and Heal lives start; without the subsystem, a per-actor life count) and writes Custom Primitive Data 1 = `FRRPulseDesync::Phase(PulseSeed, PickupDomain, id)` (uniform in [0, 1) turns) and 2 = `Rate(..., 0.8, 1.2)` with `SetCustomPrimitiveDataFloat`; index 0 (`GlowFadeDataIndex`) is not touched (padded with 0 when the array was shorter, the ore and heal materials do not read it). `ResetPulseDesync` in `OnPoolReleased` writes the neutral 0 and 1 back and clears the id. XP pickups never write indices 1 and 2 (XP and ore are different actor classes, so no pooled actor changes type). Task-267-01: the material parameter defaults do NOT apply: an unwritten Custom Primitive Data slot reaches the GPU as 0 (engine source and numbers in [[sys-grid-deposits]]), so on the XP pickups M_XPNutGlow reads PulseRate 0 and the pulse is frozen since task-257-01 (measured: BP_PickupXP mesh holds 1 float, the glow fade at 0, so slot 2 = 0); fix pending in M_XPNutGlow ([[bp-pickup-xp]]). Ore and heal pickups write slot 2 (0.8-1.2) and pulse. Same seed and spawn order give the same values; helper and crystal side in [[sys-grid-deposits]]. Check: `RogueRigs.PulseDesync.SeededValues`. Unverified: the look on screen.
