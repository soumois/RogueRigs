# Cost log

- Source: `node vault/scripts/agent-usage.js` (`--json`, `--from <n>`, `--snapshot`, `--agent-debug`). It reads this machine's Claude Code transcripts and counts every API call once. A worker is matched to its subtask by the id at the start of its description (delegations must start with it); an executor, or a legacy orchestrator launched with "Run global task", is the pilot of the first task number in its prompt; planners and legacy planning passes are listed apart (they create tasks after their prompt, so none is guessed); main sessions are listed one by one.
- Agent debug trace: `record-cost.js` refreshes the snapshot with `--agent-debug` at every task close, capturing planners and BP/C++ agents. Run `node vault/scripts/agent-usage.js --agent-detail <agent-id>` to inspect exact token usage and weighted units per API call, context size and next-call context delta, plus approximate text sizes for user messages, tool inputs and tool results. It also shows direct file reads/writes, aggregate task-node/index accesses and known task workflow scripts with invocation outcomes. Debug processing is local and adds no model calls; it only makes the snapshot larger. Size estimates use text characters / 4 and are not billed-token attribution. The trace stores no command text, file contents, task identifiers or individual task paths. Context delta includes all intervening messages and tool results, so it is not attributable to one action. Older snapshot-only sessions retain aggregate totals.
- Columns are billed separately and at different prices: input (uncached), cache write (context written to the prompt cache), cache read (context re-read from the cache on each turn, the cheapest but by far the largest), output (the most expensive per token).
- Unit (M): input-token equivalents, weights in `vault/scripts/cost-rates.json` (cache write x1.25, cache read x0.1, output x5), one comparable column. Dollar amounts appear only once `usdPerMillionInputTokens` is filled there: open, no price entered. A `~` marks a row derived from rounded columns (rows before 2026-10-26 have no turns).
- Runs: agent launches. Turns: API calls of the subtask. Resumes: messages sent to an agent after it started; the cause (turn-limit, rate-limit, message) is in the subtask `usage` line.
- Snapshot: `vault/scripts/usage-snapshot.json`, refreshed at each closing, keeps every agent and session record because Claude Code deletes old transcripts (on 2026-10-26, 566 of 665 subtask rows no longer had theirs). Planner traces include per-call usage and tool/path activity when the source transcript is available.
- Alerts: `record-cost.js` prints an ALERT when the subtask's `units` exceed `token_ceiling` written `<x> M units` (a legacy ceiling without `M units` gives none), a start context over 25k, a turn-limit resume or 55 turns, and any resume (write its cause in the subtask `result`). `task-status.js` refuses `status=done` while `tokens` is `open`.
- Not covered: tasks 000 to 012 (their agents carry no subtask id in the description).
- Per global task: a subtask done by the executor itself says `included in the executor run`; the executor run and the task's planner share are written on the global node (`executor_tokens`, `executor_usage`, `planning_tokens`, `planning_usage`) by `task-cost.js`, called by `record-cost.js` at each closing (`--all` rewrites every task). A planner is split equally over the global tasks of the `Saved/Planner/*.spec.js` files it wrote; one without spec is attributed to none. The crew-board mod adds both to the task total.
- Each finished subtask adds a row ([[orchestration-protocol]] step 5).
